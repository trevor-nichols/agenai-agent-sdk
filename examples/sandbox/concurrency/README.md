# Concurrent restricted Desktop sandboxes

This credential-free workflow uses installed public `@agen-ai/sandbox`, `@agen-ai/sandbox/node` and `@agen-ai/sandbox-docker` entrypoints. It demonstrates two independently owned members of one already activated original Desktop coordinator. It then cancels, stops, exports and destroys the selected first member, adds an independent replacement while the survivor remains active, and removes the remaining members.

The caller prepares the physical Engine, original coordinator and route authority, native helpers, pinned workload/helper images, finite resources, private namespaces and spill directories before invoking the workflow. Each member input contains a distinct explicitly coordinated backend, restricted-HTTPS request with a read/write file grant, original recovery persistence callback, positive HTTPS fixture, forbidden marker fixtures and fresh absolute host export destination. The replacement needs its own backend and storage and a policy distinct from the selected survivor. The workflow does not initialize, activate or close the shared coordinator.

The workload image must contain `/usr/local/bin/node`, `git` on `/usr/local/bin:/usr/bin:/bin`, trusted public certificate roots and the admitted non-root user. The fixed primary uses no model, credentials, ambient Git configuration or networked Git commands. Helpers and images are explicit caller assets; this example never builds or pulls them.

Import `runConcurrentSandboxWorkflow` and its types from the compiled `concurrency/index.js`. Supply:

- `coordinator`: the original active public coordinator.
- `members: [a, b]` and `replacement: c`: independent member inputs. Each contains `backend`, `request`, `recovery`, `positive`, `forbidden` and `destination`.
- `startMode`: `prepare_both` prepares both workspaces before either primary dispatches; `staged_addition` keeps A's original primary active while B prepares and dispatches. Swap the supplied profile assignments to exercise the other role order.
- `removalOrder`: `['a', 'b']` or `['b', 'a']`.
- `operationTimeoutMs`: an explicit individual observation bound between 1,000 and 30,000 milliseconds. This does not impose a primary execution deadline.
- Optional `signal`, per-member `transferOptions`, awaited `onObservation` and awaited `onOutput` evidence callbacks.

Each `positive` fixture has `hostname`, `port`, `path`, exact `status`, `bodyBytes` and `bodySha256`. Its authenticated HTTP/1.1 TLS endpoint must support repeated HEAD requests with keep-alive on one connection and GET responses with the selected stable body identity. The original primary actively sends a bounded HEAD probe every second over its original socket. A closed socket, refused keep-alive, certificate change or missing fresh response fails the workflow. Each continuity check also makes a fresh authenticated connection and validates the exact GET response. Policies must admit their own fixture and omit their peer's fixture; the replacement omits the survivor's fixture.

Each forbidden fixture contains `hostname`, explicit IPv4 `address`, `port`, `transport: 'tcp' | 'udp'`, `probe` and `marker`. At most twelve controls belong to each member. Initial admission also requires the complete serialized command to fit 16 KiB and its maximum bounded observation to fit 32 KiB; oversized aggregate fixtures reject before reservation. Direct diagnostics retain at most 64 code characters and 256 message characters. Direct probes have a 750 ms observation bound and run concurrently; each also requires a broker CONNECT denial. A TCP connection or UDP response fails immediately. UDP silence alone does not prove isolation: the caller must independently prove the same address/port/protocol reachable and compare the controlled listener's monotonic counters before and after the exact original-primary probe. An empty fixture list exercises only cross-policy CONNECT denial and cannot establish the native forbidden-service rows.

The fixed immutable source and instruction bytes are copied into each workspace's read-only `inputs/`. Each original primary creates a detached local Git repository under its own `project/.git` with separate objects, index, refs and config, empty hooks and no remotes or alternates. It continuously writes atomic project counters and emits ordered stdout ticks. A fatal background file or held-TLS failure closes its original command input, joins its background/network work and exits with code 1 while retaining stderr evidence. Same-path project and auxiliary native-state mutations remain member-specific. Initial instruction/source hashes, original process and reader identities, Git state, fresh file work and held/fresh TLS results are verified throughout the transitions.

For each live-file observation, the existing inspect command copies a published counter into a fresh auxiliary file and acknowledges its path, size and hash after closing it. The SDK read must complete with those exact bytes while the original counter writer continues. The workflow then requires further ticks and held-TLS progress. Each snapshot is at most 4 KiB, is never replaced, and remains under `native-state/observations/` until member cleanup, bounded by the existing 192-command limit. This fixture avoids assuming that a concurrent read of a changing pathname returns complete JSON; it does not add an atomic-snapshot guarantee to the SDK.

Every before/after lifecycle event contains a monotonically increasing sequence and the available original owner/process/reader identities, coordinator state and original recovery record. `continuity_before` precedes each control batch, and `continuity` carries its concrete result. Its `checkpoint` names the transition and whether the peer observation occurred before, after entry or after settlement. `onOutput` receives the original unmodified stdout/stderr chunks from the sole reader before parsing. Callers must retain those bytes with explicit completeness/truncation status and independently verify Engine/process cleanup. The session bounds stdout to 4 MiB, stderr to 64 KiB, commands to 192 per member and file/output ticks to 4,800. Requests must supply stream capacities sufficient for those declared bounds; all members retain separate stream and transfer budgets.

A final export occurs only after original process, sandbox writers and original output readers settle. The export selects the `project` subtree, including its independent Git tree, and verifies the resulting host tree. `inputs/`, `native-state/` and `.concurrency/` stay outside that selection. Successful results retain the stopped export directory, process exit and final original recovery record for each member.

`ConcurrentSandboxWorkflowError` retains `primaryFailure.error`, separate `cleanupFailures`, every original `ownedMembers` reservation and reusable `retryCleanup()`. If shared authority remains active, failure handling first tries fresh work through still-ready original peers and emits `cleanup_continuity_before` / `cleanup_continuity`; a failed continuation remains a separate failure. Group fencing does not become a successful local continuation. Cleanup never adopts new authority, reconstructs a primary, replaces its reader or replays work. A successful cleanup retry does not rewrite the original failure. Coordinator settlement/closure remains the caller's obligation after exact original member cleanup.

Run the focused local test from the standalone SDK checkout with:

    node --import tsx --test examples/sandbox/concurrency/tests/*.test.ts

These tests execute the fixed guest with real local Node processes and finite Git commands. The network diagnostic test uses a loopback-only CONNECT proxy and TLS fixture with a synthetic certificate trusted only by its child process. It checks original-connection failure evidence and socket settlement without Docker or internet access. Installed compilation, actual coordinator lifecycle and native Desktop network/process/resource qualification remain separate proof layers.
